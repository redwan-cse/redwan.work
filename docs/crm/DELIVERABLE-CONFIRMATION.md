# Locked deliverable confirmation

Migration 0032 adds a service-only confirmation RPC. The existing server action still requires current admin authority and validates full file scope, extension/MIME and actual stored length before invoking the file service. SQL rechecks the current actor's active profile, matching Auth admin role and ban, locks the unarchived parent project, validates the current owner namespace and metadata, then locks the storage key shared with cleanup tombstones. It either inserts once or returns the exact existing binding; changed-payload reuse is refused. Transactional email events therefore occur once per inserted file, not per retry.

The parent lock closes the archive-between-HEAD-and-insert race: if archive wins, confirmation waits then refuses; if confirmation wins, the archive's complete snapshot comparison sees the new file and refuses stale backup proof. Credential revocation after a valid request began still follows transaction ordering, not external-time atomicity. Storage HEAD and SQL remain separate services, so no distributed transaction or prevention of later object overwrite is claimed.

The disposable database test verifies exact concurrent replay, invalid/foreign scope, metadata, actor privilege, and a lock-observed archive/confirmation race. It keeps an archive transaction open, waits until pg_stat_activity proves confirmation is blocked on a lock, then commits archive and asserts no late file insertion. Synthetic fixtures are deleted exactly. The normal restore path remains available to privileged verified-snapshot tooling; a blanket archived-file trigger was deliberately not introduced because it would obstruct recovery.

Apply forward migration before the matching service code. On rollback retain the additive RPC and prefer forward fixes; old direct insertion would reopen the race. Production SQL/storage/credentials were not accessed. Individual file deletion and restore policy are distinct from this confirmation transaction and require their own review.
