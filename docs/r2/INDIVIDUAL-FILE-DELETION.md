# Individual-file deletion safety

Previously deleteOwnedFile removed R2 bytes before deleting the database row. A later database failure could leave a visible file with missing bytes, and a concurrent archive could race physical deletion. Migration 0034 adds a service-only prepare_file_deletion transaction using the existing durable storage_deletions queue and tombstones.

The transaction validates current profile/Auth role, activity and ban, serializes same-file requests, locks an unarchived project or owning ticket, preserves the existing client attachment uploader/24-hour restriction, locks the storage key, and rechecks the complete file snapshot. It refuses retained lead references. It inserts durable snapshot/actor/file tracking and removes the visible row atomically. No object bytes are touched until this commits. Archived project files refuse individual removal; project cleanup remains its separately verified workflow.

The application attempts one physical deletion only after preparation, then acknowledges it. Provider or acknowledgement failures retain a retryable queue record. Same-actor retries find the queued/completed operation rather than treating a removed row as unknown. Current authority is rechecked on retry; another actor cannot use the retry lookup to obtain the key. The existing bounded storage cleanup worker drains these jobs too. Existing signed links can remain usable until expiry or physical deletion; the UI must not claim instant revocation of issued URLs. Tombstones refuse later database rebinding, not arbitrary privileged R2 writes.

This changes deletion ordering, not retention policy: no new archive expiry or account-erasure policy is invented. File metadata is retained for audit/retry; no recovery copy of a user-requested individual deletion is promised. Existing applied migrations stay unchanged. Apply 0034 through a separately authorized schema-first rollout; no production operation occurred during development. Retain the additive queue metadata on application rollback and prefer a forward fix over returning to storage-first deletion.

Required evidence: regression must fail against the old service because object deletion occurs before preparation; new runtime refusal/failure/replay cases; disposable SQL rollback, current role, ownership, archive and late-reference refusal; actual disposable storage cleanup. Production backup/host configuration remains separate.
